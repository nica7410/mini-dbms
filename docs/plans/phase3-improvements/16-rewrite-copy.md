# 16. 임시 파일 쓰기 최적화 — 바뀐 행이 나온 뒤에만, 원래 바이트로 복사

작성일: 2026-11-18  
기준 커밋: `f89f37c` + 미커밋 11·13·15-A 변경 (브랜치 `feat/phase3-cpp`)  
상태: 완료(2026-11-18). 결과는 [6절](#6-결과-2026-11-18).

## 1. 문제와 근거

2026-11-18 사용자 선택: "임시 파일 최적화"([11번 판단](11-modify-cost.md#판단)의 선택지 (a)).

[11번 측정](11-modify-cost.md#8-결과-2026-11-18)(100만 행, 중앙값)으로 보면 UPDATE·DELETE 비용의 대부분은 교체·`fsync`가 아니라 임시 파일 쓰기다.

| 문장 | 컨테이너 | Windows |
|---|---:|---:|
| 한 행 변경 `update_id_hit` | 242 ms | 536 ms |
| 0행 변경 `update_age_miss`(교체·`fsync` 없음) | 174 ms | 444 ms |
| 전체 읽기 `select_scan` | 46 ms | 52 ms |

지금 `table_rewrite`가 하는 일:

- 임시 파일을 먼저 만든다.
- 바뀌지 않은 행까지 모두 `fprintf`로 다시 형식화해 쓴다.
- 일치하는 행이 없으면 다 쓴 파일을 버린다.

## 2. 범위

포함(`src/storage.c`만):

- **지연 생성:** 첫 변경 행(REPLACE·DELETE)이 나올 때 임시 파일을 연다. 변경이 없으면 임시 파일을 만들지도 쓰지도 않는다.
- **원래 바이트 복사:** 바뀌지 않은 행(KEEP)은 형식화하지 않는다. 연속 구간을 원래 파일에서 블록(64 KiB) 단위로 그대로 복사한다.
  - 원래 파일은 시작할 때 정규형으로 검증됐으므로 바이트가 같다.
  - 복사용 읽기 핸들은 하나 더 연다(`rb`). `t->fp`는 스캔에 쓰고 있다.
  - 이 핸들은 교체 전에 닫는다. Windows는 열린 파일을 대체할 수 없다.
- **행 위치 전달:** `scan_rows`가 행마다 원래 파일 안의 위치와 줄 길이를 계산해 두고, 재작성 콜백에 넘긴다. 내부 함수만 바꾸며 공개 API는 그대로다.

제외:

- 새 인덱스 재구축 방식 변경. 지금처럼 행마다 `bptree_append`한다. 측정 뒤 이것이 큰 몫이면 별도로 검토한다.
- 잠금·서버·실행기 변경, `fsync` 정책 변경.

## 3. 바뀌지 않는 성질

- 결과 파일의 바이트는 지금과 같다(KEEP 행은 원래 바이트, REPLACE 행은 `fprintf` 형식).
- 실패 의미:
  - 교체 전 실패는 원본·Table을 그대로 둔다.
  - 교체 뒤 실패는 "적용됨"으로 보고하고 Table을 막는다.
- `users.meta` 규칙(13번)과 `fsync` 순서(10번 후속)도 그대로다.

## 5. 완료 기준

- 위 테스트가 통과한다.
- `update_age_miss`가 `select_scan` 수준으로 줄었고, `update_id_hit` 감소량이 기록돼 있다.

## 6. 결과 (2026-11-18)

계획대로 구현했다(`src/storage.c`만, 공개 API 변경 없음).

- `scan_rows_spans`: 행마다 원래 위치와 줄 길이를 넘기는 내부 스캔이다. 기존 `scan_rows`는 이 함수를 감싼 것이다.
- `rewrite_span`·`begin_change`·`copy_until`·`add_index_entry`
  - 첫 변경 행에서 임시 파일, 복사 핸들(`rb`), 64 KiB 버퍼를 연다.
  - KEEP 구간은 `fread`/`fwrite`로 원래 바이트를 복사한다.
  - REPLACE 행만 `fprintf`로 쓴다.
- 실패 종류 2개를 추가했다.
  - `REWRITE_TEMP_OPEN_FAILED`: "임시 파일을 만들 수 없습니다"
  - `REWRITE_SOURCE_FAILED`: "데이터 파일 복사 실패"
- 복사 핸들은 교체 전에 닫는다.
- 테스트: `test_rewrite_large_copy`. 1만 행(약 160 KB) 파일로 다음을 확인한다.
  - 가운데 행 이름을 길게 바꾼다.
  - 앞쪽 연속 두 행을 한 문장으로 지운다.
  - 파일 전체 바이트를 비교한다.
  - 끝에서 두 번째 행을 바꾼다.
  - id 조회 4건과 다시 열기를 확인한다.
- 같은 파일에 쓰려고 `tests/test_unit.c`에 `<stdbool.h>`를 추가했다.

### 측정 (중앙값 ms, 원시 출력 [results-16.txt](../../phase3-benchmarks/20261118-modify/results-16.txt))

| 문장 | 컨테이너 100만 행: 전 → 후 | Windows 100만 행: 전 → 후 |
|---|---:|---:|
| `update_id_hit` (한 행 변경) | 242.3 → **85.1** (−65%) | 536.2 → **145.6** (−73%) |
| `update_age_miss` (0행) | 174.5 → 60.0 | 443.7 → 107.6 |
| `delete_id_hit` (한 행 삭제) | 228.7 → 87.1 | 518.3 → 114.4 |
| `select_scan` (비교) | 46.0 → 45.6 | 51.7 → 52.0 |
| `delete_id_miss` | 0.000 → 0.000 | 0.000 → 0.000 |

컨테이너 1만·10만 행의 `update_id_hit`: 8.8 → 8.0, 30.1 → 13.6.

해석:

- 0행 변경(`update_age_miss`)과 전체 스캔의 차이가 컨테이너 128 → 14 ms, Windows 392 → 56 ms로 줄었다.
- 남은 차이는 임시 파일과 상관없는 새 인덱스 구축(행마다 `bptree_append`)이다. 변경이 없으면 결국 버린다. 범위 밖으로 둔 항목(2절)이며, 필요하면 "첫 변경 전까지는 인덱스도 만들지 않기"로 더 줄일 수 있다.

### 12·14번에 대한 영향

[11번 4절](11-modify-cost.md#4-판단-기준) 기준(100만 행 한 행 변경 T)으로 다시 본다.

- **컨테이너 T = 85 ms:** "100 ms 이하: 12·14번 보류"에 해당한다.
- **Windows 호스트 T = 146 ms:** 여전히 100 ms를 조금 넘는다.

11번 기준은 컨테이너 측정을 주로 삼았으므로 12·14번은 보류로 바꾸고, Windows 수치를 함께 기록해 둔다. HTTP 서버의 빌드·실행 안내는 Linux/WSL과 Docker 기준이다([server/README](../../../server/README.md)). Windows CLI에서 한 번에 146 ms가 문제가 되면 12번을 다시 검토한다.
