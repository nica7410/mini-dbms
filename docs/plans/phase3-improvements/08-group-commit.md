# 8. 묶음 쓰기(group commit)

작성일: 2026-11-17  
기준 커밋: `912d07f`  
상태: 구현 완료. 사용자가 3절의 "파일 크기로 k 계산" 방식을 선택했다. 실행 기록은 문서 끝에 있다.

## 목표

여러 행 INSERT 한 문장의 행들을 **한 번의 `fwrite` + 한 번의 `fflush`**로 기록한다. 지금은 행마다 `fprintf` + `fflush`라서 1,000행이면 `write` 시스템 호출이 1,000번 일어난다([storage.c `table_append`](../../../src/storage.c)).

기대 효과:
- 여러 행 INSERT의 C 실행 시간과 서버의 배타 gate 점유 시간이 줄어든다. 그동안 SELECT가 기다리는 시간도 줄어든다.
- 한 행 INSERT는 바뀌지 않는다. 성능도 그대로다.

얼마나 빨라지는지는 아직 모른다. 예상 수치를 적지 않고 구현 전후를 측정해서 기록한다(검증 3).

### 범위 밖
- **여러 요청을 묶는 group commit.** 서로 다른 HTTP 요청이나 CLI 문장의 INSERT를 묶는 것은 하지 않는다. 묶는 단위는 SQL 한 문장이다.
- **`fsync`.** 내구성 수준은 지금과 같다. `fflush`는 운영체제까지 넘기는 것이지 디스크 기록을 보장하지 않는다.
- **stdio 버퍼 재기록 한계 해결.** 쓰기에 실패한 데이터가 stdio 버퍼에 남았다가 `fclose`에서 다시 쓰일 수 있는 문제(07의 남은 한계)는 이번에 고치지 않는다.

## 지금 구조에서 지켜야 할 것

| 항목 | 현재 동작 | 묶음 쓰기 후 |
|---|---|---|
| 값 검증 | 모든 행을 검증한 뒤 기록한다(07). 값 오류면 0행 | 같음 |
| ID | 한 문장의 ID는 연속. `last_id`는 쓰기 성공 뒤에만 올림 | 같음. 묶음 전체가 성공하거나, 기록된 행까지만 올림 |
| 인덱스 | 쓰기 전에 리프 자리를 확보하고(`bptree_reserve_append`), `fflush` 성공 뒤 키를 공개 | 아래 2절 |
| 부분 기록 | 중간 행에서 실패하면 앞의 k행은 기록, 실패한 행은 `unknown`. 서버는 `partial` + 범위 | 같은 계약을 유지한다. k는 아래 3절 방식으로 정한다 |

## 설계

### 1. 저장 API

`storage.h`에 묶음 함수를 추가한다. 저장 계층이 파서의 `InsertRow`에 의존하지 않도록 저장용 구조체를 따로 둔다.

```c
typedef struct {
    const char *name;
    int age;
} AppendRow;

/*
 * rows를 순서대로 연속 ID로 추가한다. 한 번에 쓰고 한 번 flush한다.
 * 성공: 0, *stored == n. 실패: -1, *stored는 파일에 완전히 기록된 앞쪽 행 수.
 * first_id는 첫 행의 ID(stored > 0일 때만 의미가 있음).
 */
int table_append_rows(Table *t, const AppendRow *rows, size_t n,
                      int64_t *first_id, size_t *stored, DbError *err);
```

- 기존 `table_append`는 `n == 1`로 이 함수를 부르는 얇은 함수로 바꾼다. 시그니처와 동작은 그대로다.
- executor의 `run_insert`는 검증이 끝나면 `InsertRow` 배열을 `AppendRow` 배열로 옮겨 한 번 호출한다. 배열은 최대 1,000개라 16KB 이하다.
- 호출이 끝난 뒤 `on_insert`를 기록된 행마다 순서대로 부른다. 서버의 `record_insert`는 바꾸지 않는다.
- 기록된 행이 k > 0개인데 실패하면, 지금처럼 메시지 앞에 `앞의 k행은 기록됨:`을 붙인다.

### 2. 쓰기 순서

```text
검사: table_usable, 각 행의 저장 가능 여부, ID가 INT64_MAX를 넘지 않는지(last_id + n)
  → 모든 행을 메모리 버퍼 하나에 "id\tname\tage\n"으로 만든다. 행마다 끝 위치를 기록한다
  → fseek(END) + ftell 한 번으로 시작 위치 start를 구한다
  → 인덱스: 행마다 reserve_append → append(id, start + 행 시작 위치)
  → fwrite(버퍼 전체) + fflush 한 번
  → 성공: last_id += n
  → 실패: write_failed = true, 기록된 행 수 k 계산(3절), last_id += k
```

- **버퍼 크기.** 한 행은 최대 19(ID) + 1 + 255 + 1 + 3 + 1 = 280바이트다. 1,000행이면 약 280KB를 한 번 할당한다. 할당에 실패하면 아무것도 쓰지 않고 오류를 낸다. 0행 기록이며 테이블은 계속 쓸 수 있다.
- **행마다 `fseek`하지 않는다.** 출력 스트림에서 `fseek`을 하면 버퍼가 비워진다. 그래서 시작 위치를 한 번 구하고, 각 행의 오프셋은 버퍼 안 위치를 더해 계산한다. 파일은 `"a+b"`로 열려 있어 쓰기는 항상 파일 끝에 붙는다.
- **인덱스 키를 쓰기 전에 넣는 이유.** 지금은 리프 자리를 먼저 확보하고 쓰기가 성공한 뒤 키를 넣는다. 그런데 B+ 트리는 한 번에 한 자리만 확보할 수 있다(`bptree_reserve_append`). 그래서 n개 키를 쓰기 뒤에 넣으면, 파일에는 기록됐는데 중간에 메모리가 부족해 인덱스에서 빠지는 행이 생길 수 있다. 반대로 키를 먼저 넣으면 다음 이유로 안전하다.
  - 키를 넣는 동안과 쓰는 동안에는 reader가 실행되지 않는다. 서버는 배타 gate를 잡고 있고, CLI는 단일 스레드다.
  - 쓰기에 실패하면 `write_failed` 때문에 테이블 전체가 사용 불가가 된다. 그러면 파일에 없는 행을 가리키는 키를 아무도 읽지 않는다. 재시작하면 인덱스를 파일에서 다시 만든다.
- **키를 넣다가 메모리가 부족할 때(j번째 행).** 이미 키를 넣은 앞의 j행만 쓰고 flush한 뒤 실패를 반환한다. 07의 부분 기록과 같은 결과(`앞의 j행은 기록됨`, 서버 `partial`)다. j = 0이면 아무것도 쓰지 않는다. 이 경우는 쓰기 실패가 아니므로 테이블을 계속 쓸 수 있다.

### 3. 쓰기에 실패했을 때 기록된 행 수 계산

행마다 flush하던 때는 "몇 번째 행에서 실패했는가"가 곧 기록된 행 수였다. 한 번에 쓰면 `write`가 일부만 쓰고 실패할 수 있다(예: 파일 크기 제한, 디스크 가득 참). 그래서 실패한 직후 파일 크기를 직접 확인한다.

- POSIX에서는 `fstat(fileno(fp))`, Windows에서는 `_fstat64(_fileno(fp))`를 쓴다. 기존 `file_seek`/`file_tell`처럼 storage.c 안에 플랫폼별 매크로로 둔다.
- `기록된 바이트 = 파일 크기 - start`. 끝 위치가 이 값 이하인 앞쪽 행이 k개다. 줄 중간에서 끊긴 행은 기록되지 않은 것으로 센다(지금의 `unknown`과 같음).
- 파일 크기를 확인하지 못하면 k = 0으로 보고한다. 이때 서버는 지금처럼 `unknown`을 돌려준다. 실제보다 적게 보고할 수는 있어도 많게 보고하지는 않는다.

**선택지 (사용자 결정 필요).** 3절 대신 "묶음 쓰기에 실패하면 문장 전체를 `unknown`으로 보고"하는 더 단순한 방법도 있다.

| | 파일 크기로 k 계산 (권장) | 문장 전체 `unknown` |
|---|---|---|
| 07의 `partial` 계약 | 유지 | 쓰기 실패에는 더 이상 `partial`이 나오지 않음. 메모리 부족 때만 남음 |
| 코드 | 플랫폼별 `fstat` 매크로와 행 끝 위치 배열이 필요함 | 단순함 |
| 클라이언트 | 재시도할 범위를 정확히 앎 | 모든 행을 직접 확인해야 함 |

07에서 막 공개한 응답 계약을 유지하려면 파일 크기 방식이 맞다. 이 문서는 그 방식을 기준으로 쓴다.

### 성능 (C 벤치마크, 3회 번갈아 실행)

기준은 `912d07f`의 `src`에 같은 `tests/benchmark.c`를 붙여 빌드했다. 단위는 초.

| 측정 | 기준 1·2·3회 | 변경 후 1·2·3회 | 중앙값 |
|---|---|---|---|
| 1,000행 INSERT 1,000문장(100만 행) | 3.547, 2.916, 3.293 | 0.198, 0.195, 0.268 | 3.293 → 0.198 (약 17배) |
| 한 행 INSERT 100만 문장 | 4.266, 3.310, 3.193 | 3.568, 3.268, 3.865 | 3.310 → 3.568 |

- 다중 행 INSERT는 행당 약 3.3µs에서 약 0.2µs로 줄었다. 대부분 행마다 하던 `write` 시스템 호출 비용이었다.
- 한 행 INSERT는 두 쪽 모두 3.2~4.3초 사이에서 흔들려 차이를 판정할 수 없다. 이 측정 당시 executor에는 한 행에도 `malloc`이 있었다(리뷰 지적, 이후 제거). 제거 후 다시 측정하지 않았다. 확인하려면 반복 횟수를 늘려야 한다.
- 서버 HTTP 처리량·gate 점유 시간은 측정하지 않았다(최소 실행 원칙).

### 남은 한계

- 쓰기 실패 뒤 stdio 버퍼에 남은 바이트가 `fclose`에서 다시 쓰일 수 있다(07과 같음). 보고한 k는 실패 직후의 파일 크기 기준이다.
- 인덱스 메모리 부족 경로(키를 넣다가 실패해 앞쪽 행만 쓰는 경우)는 자동 테스트가 없다.
- `fsync`는 하지 않는다. 여러 요청을 묶는 group commit도 하지 않는다.
