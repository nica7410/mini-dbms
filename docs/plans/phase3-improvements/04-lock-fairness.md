# 4. 읽기 진행과 잠금 공정성 평가

상태: 완료 — 평가, 후보 실험, 판단 모두 끝남. **현재 쓰기 우선 정책 유지(후보 미채택)**  
후보 실험(축소 범위):
- 티켓 gate `server/benchmarks/fair_gate.hpp`를 벤치마크 전용 빌드로만 연결했다.
- gate 순서 시나리오 2개, TSan, Release ctest를 통과했다.
- write99, worker 8, 3회 비교 결과:
  - 읽기 p99: 120–131ms → 4.4ms
  - 처리량: −34%
  - 쓰기 p99: +30%
- D절에 따라 채택하지 않았다.


평가 결과: worker 8의 쓰기 99% 포화 부하에서 읽기 p99가 쓰기 p99의 약 38배였다(반복 3회 모두). 읽기 무진행 구간은 최장 0.11초였다. 근거는 [minimal-report.md](../../phase3-benchmarks/20261116/minimal-report.md)에 있다.  
기존 논의: 4번  
선행 작업: [지표와 성능 비교](03-metrics-and-benchmarks.md)

사용자 정정(2026-11-16): 필수 테스트만 최소 실행한다. 이 문서의 반복 측정·후보 비교 요구를 근거로 장시간 검증을 자동 실행하지 않는다. 현재 정책은 변경하지 않았고, 공정성 평가도 완료하지 않았다.

## 해결할 문제와 정확한 전제

현재 gate는 대기 writer가 있으면 새 reader의 진입을 막는다. 이는 쓰기 우선 정책이며 reader의 최대 대기시간을 보장하지 않는다.

worker 수는 동시에 존재하는 writer 수를 제한할 뿐, 새로운 INSERT의 연속 도착이나 reader의 전체 대기시간에 상한을 주지 않는다. INSERT가 보통 짧다는 관찰도 파일 I/O 시간의 보장이 아니다. 반대로 공정한 gate를 구현하더라도 느리거나 끝나지 않는 I/O 때문에 벽시계 기준 응답시간을 보장할 수는 없다.

이 작업의 필수 산출물은 측정 근거를 포함한 **현재 정책 유지 또는 변경 판단**이다. 정책 변경 자체를 선결론으로 삼지 않는다.

## A. 필수 평가

1. 3번의 지속적인 쓰기·읽기 혼합 결과를 확인한다. 요청 종류별 제출·완료·미완료 수, p95/p99, read/write gate 대기 시간을 함께 본다.
2. 큐에서 밀린 시간과 gate에서 밀린 시간을 구별한다. 모든 worker가 대기 중인 상황, 큰 스캔의 보유 시간, generator 병목을 gate 정책의 문제와 혼동하지 않는다.
3. 읽기와 쓰기가 모두 제출된 측정 구간에서 writer는 계속 완료되는데 reader의 완료가 장시간 멈추는 구간이 있는지 확인한다. 독립 반복 3회에서 확인하고 미완료 reader를 결과에서 제외하지 않는다.
4. 기존 테스트의 writer 우선 순서는 정책을 설명하는 테스트이지, reader 지연이 작음을 입증하는 테스트가 아님을 명시한다.
5. 사용자 지정 SLO가 있다면 같은 부하 조건에서 대조한다. 현재는 SLO가 없으므로 임의의 ms를 허용 한도로 확정하거나 무조건적인 '문제 없음' 판정을 하지 않는다.

## B. 정책 후보 실험을 시작하는 조건

다음 중 하나가 있으면 공정한 후보의 구현·비교를 진행한다.

- 지원하려는 부하에서 writer 완료가 지속되는 동안 대기 reader가 측정 구간 내 진행하지 못하는 현상이 반복되고, gate 대기와 관련됨을 확인했다.
- 향후 명시된 읽기 SLO를 만족하지 못하고 read gate 대기가 주요 원인임을 확인했다.

이 조건이 없으면 현재 정책을 유지하고, 측정한 범위와 아직 보장하지 않는 최대 대기시간을 기록한다. 포화·과부하 조건의 긴 지연만으로 정책 결함을 단정하지 않는다. 측정 구간의 무진행은 기아 위험의 관측 근거이며 무한 기아를 수학적으로 증명한 것으로 표현하지 않는다.

## C. 조건 충족 시 구현할 후보

단순 reader 우선 전환은 하지 않는다. 내부 gate에서 도착 순서를 기록하는 티켓/대기열 기반 후보를 구현한다.

- 도착 순서는 HTTP 수신 순서가 아니라 **gate 대기 등록 순서**로 정의한다.
- writer는 배타 진입한다. 큐에서 연속된 reader는 함께 진입할 수 있으나, 먼저 등록된 writer를 뒤의 reader가 건너뛰지 않는다.
- 먼저 대기 중인 reader 그룹도 나중 writer가 계속 추월하지 못한다.
- 기존 reader mutex → gate → writer mutex 순서, 성공 INSERT 범위 추적, 장애 상태 전파를 유지한다.
- 대기 노드·ticket의 수명, 예외 시 등록 해제, notify 누락, spurious wakeup을 처리한다. 유한 정수 ticket을 쓴다면 wraparound 처리 또는 발생 조건을 명확히 한다.
- 새 timeout/취소 기능을 함께 넣지 않는다. gate를 공정하게 만드는 것과 실행 중 I/O를 취소하는 것은 별도 작업이다.
- 독립 gate 구현과 테스트를 먼저 완성하고, 기존 서버와 비교할 별도 빌드 타깃으로 연결한다. 측정 전 운영 기본 정책을 바꾸지 않는다.

## D. 후보 검증과 채택 판단

- gate 등록 상태를 확인하는 확정적 테스트로 reader→writer→reader, writer→reader→writer, reader 그룹, 연속 writer와 먼저 등록된 reader의 순서를 검증한다.
- 엔진 통합, SIGTERM drain, 신규 ID 조회, 실패 전파 테스트를 모두 통과해야 한다. 지원 환경에서 TSan을 실행한다.
- 3번과 동일한 데이터·offered load·worker·연결·반복 조건으로 기존 정책과 비교한다. 읽기 지연 개선뿐 아니라 쓰기 지연, 처리량, 거절률, 메모리를 함께 보고한다.
- 독립 반복에서 읽기 진행 개선이 확인되고, 다른 주요 지표에 반복 변동을 넘어서는 악화가 없으면 채택 근거로 삼을 수 있다.
- 읽기 개선과 쓰기/처리량 악화가 함께 나타나면 자동 채택하지 않는다. 결과와 선택지를 기록하고 필요한 서비스 목표를 명시한다. 현재 요청만으로 임의의 성능 희생 허용치를 정하지 않는다.
- 채택 시 기본 gate 연결과 정책 문서·테스트 기대 순서를 함께 갱신한다. 이전 구현은 비교와 되돌리기에 필요한 식별자를 남긴다.

## 산출물과 완료 기준

- `docs/phase3-benchmarks/` 아래 공정성 판단 보고서: 환경, 부하, 결과, 유지/후보 실험/채택/보류 판단과 근거.
- 유지 판단이면 측정한 범위에서 코드 변경 없이 완료할 수 있다. 읽기 최대 대기시간 보장은 여전히 없음을 적는다.
- 후보 실험이 필요하면 구현·테스트·동일 부하 비교까지 수행한다. 근거 부족이나 목표 미정 때문에 채택이 보류되면 그 단계를 완료로 표시하지 않는다.
- 정책 변경을 채택한 경우 관련 문서, API 계약 보존 확인, 회귀 검증 결과까지 남긴다.

## 제외 범위

절대 응답시간 보장, SQL 취소, 강제 thread 종료, MVCC, 트랜잭션, writer 병렬화, reader 인덱스 재구축은 포함하지 않는다.
