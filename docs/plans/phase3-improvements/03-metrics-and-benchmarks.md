# 3. 잠금 지표 분리와 재현 가능한 성능 비교

상태: 완료 — 측정은 [05 최소 검증](05-minimal-verification.md) 범위(27개 조건)로 대체해 수행했다. 결과: [minimal-report.md](../../phase3-benchmarks/20261116/minimal-report.md)  
기존 논의: 3번  
선행 작업: [fallback 범위 제한](01-fallback-range.md), [동시성 검증](02-concurrency-tests.md)  
다음 작업: [공정성 판단](04-lock-fairness.md)

사용자 정정(2026-11-16): 필수 테스트만 최소 실행한다. 아래 전체 매트릭스와 추가 반복 계획은 자동 실행 대상에서 제외하며 별도 명시적 요청 없이 재개하지 않는다. 이미 얻은 결과를 보존하고, 불완전한 측정을 전체 완료로 보고하지 않는다.

## 목표

현재 단일 `lock_wait_us`로는 읽기·쓰기·fallback 중 어디에서 대기하는지 알 수 없다. 실제 HTTP 성능과 변경 효과를 부하별로 측정하고, 다음 단계의 잠금 정책 판단에 필요한 근거를 만든다.

## A. 서버 지표의 확정 계약

기존 `engine.lock_wait_us`를 유지하고 아래 다섯 범주를 모두 추가한다. 세 범주만 추가하고 나머지 대기의 포함 관계를 불명확하게 남기지 않는다.

| 범주 | 측정 구간 |
|---|---|
| `reader_mutex` | worker reader 컨텍스트 mutex 획득 |
| `read_gate` | SELECT의 공유 gate 획득 |
| `write_gate` | INSERT의 배타 gate 획득 |
| `insert_writer_mutex` | INSERT의 writer mutex 획득 |
| `fallback_mutex` | ID 재조회의 writer mutex 획득 |

추가 JSON 필드는 `engine.lock_wait.<범주>.count`, `.total_us`, `.max_us`로 정한다. C++에서도 동일한 범주를 표현하는 통계 구조를 사용한다.

- count는 성공한 잠금 획득 횟수다. 실제로 경합한 횟수라고 설명하지 않는다. 즉시 획득한 경우도 포함한다.
- 시간은 monotonic clock으로 획득 직전부터 직후까지 측정한다. 잠금 보유 시간과 SQL 실행 시간은 포함하지 않는다.
- microsecond 미만의 값은 0이 될 수 있으며 측정 자체의 비용도 기록한다. 평균은 `total_us / count`이고 count가 0이면 정의하지 않는다.
- 기존 `lock_wait_us`에는 같은 다섯 범주의 시간을 반영한다. 작업이 모두 끝난 시점에는 합계가 일치해야 한다. 실행 중 독립 atomic snapshot의 차이는 문서화한다.
- 서버에 p95/p99 histogram을 새로 구현하지 않는다. 요청별 전체 지연은 클라이언트에서 측정한다.
- 기존 `execution_us`, 요청·오류·fallback·큐 지표의 의미를 유지한다.

변경 대상은 `server/engine.cpp`, `engine.hpp`, `main.cpp`, 관련 테스트와 문서다. 계측 테스트는 횟수·분류·합계·max 관계를 검증하며 1us 이상이어야 한다는 속도 의존 assertion은 쓰지 않는다.

## B. 비교 대상

### 필수: 같은 구현의 직렬 DB 실행과 병렬 조회

일반 서버와, 모든 DB gate 획득을 배타 처리하는 별도 benchmark 타깃을 비교한다. 두 타깃은 같은 코드·컴파일 옵션·지표·HTTP/SQL 처리와 W개의 reader 컨텍스트를 사용한다. 직렬화 타깃은 내부 gate 타입을 빌드 시 선택하며 운영 CLI에 benchmark 옵션을 추가하지 않는다.

이 기준선은 **동일한 reader 구성에서 DB 실행을 직렬화한 비교군**이다. 단일 Table 구현으로 부르지 않는다. 따라서 Table 수 감소에 따른 시작 시간·메모리 이득을 측정한 것으로 해석하지 않는다. 단일 Table 전용 서버의 별도 구현은 이번 범위에서 제외한다.

### 필수: 상한 최적화 전후의 제한된 비교

1번 변경의 효과는 기존 `2cccc9b`와 상한 최적화 이후 버전을 별도 임시 소스 복사본에서 빌드해 비교한다. 없는 큰 ID 부하를 대상으로 worker 1·4개에서 확인한다. 내부 지표 구성이 다르면 공통 HTTP 지연·처리량·fallback 수만 직접 비교하고, 지표 분리 비용까지 포함된 차이임을 명시한다. 다른 변경이 섞여 효과를 분리할 수 없다면 해당 비교를 최적화의 인과 증거로 쓰지 않는다.

## C. 부하와 데이터

기본 데이터는 100만 행으로 고정한다. smoke 실행만 작은 fixture를 허용한다. SQL 출력 행 수가 결과 상한에 걸리지 않도록 스캔은 적은 수의 행에만 일치하는 age 조건으로 전체 파일을 탐색한다.

| 부하 | 구성과 판정 |
|---|---|
| 기존 ID | 시작 fixture 내 ID를 고정 seed로 무작위 조회; 행 내용 검증 |
| 신규 ID | 서버 시작 후 준비 단계에서 일정 수 INSERT하고 그 ID 조회; 준비 작업은 측정에서 제외 |
| 없는 ID | 초기 ID gap, 음수/0, 마지막 성공 ID보다 큰 값으로 구분; 상한 최적화 후 fallback이 0인지 확인 |
| 스캔·쓰기 혼합 | 스캔과 INSERT를 같은 측정 구간에 동시 제출; 예: 요청 수 기준 스캔 90%, INSERT 10%; 비율을 설정·기록 |
| 지속적인 쓰기와 읽기 | 기존 ID SELECT와 INSERT를 동시에 유지; 쓰기 비율 50%, 90%, 99%를 단계적으로 비교; 읽기/쓰기 완료와 지연을 따로 집계 |

모든 반복은 같은 fixture의 새 임시 DB에서 시작한다. INSERT로 파일이 커지는 양, 준비 INSERT 수, 성공 ID를 기록한다. 없는 ID의 상한은 해당 실행의 최대 INSERT 예산보다 크게 잡아 실수로 존재하는 ID가 되지 않게 한다. 워밍업 쓰기는 별도 예산에 포함하고 측정 시작 시 실제 파일 상태를 기록한다.

## D. 부하 생성기와 측정 방법

- `server/benchmarks/`에 재현 가능한 runner와 사용 설명을 추가한다. 테스트용 제어 코드를 포함하지 않은 Release 서버를 사용한다.
- worker 1·2·4·8개, HTTP I/O thread 수·큐·timeout·연결 재사용 정책은 동일하게 고정한다.
- 고정 동시성 모드로 최대 처리량 경향을 보고, 고정 도착률 모드로 동일한 외부 부하에서 지연·거절을 비교한다. 하나의 모드 결과를 다른 모드로 해석하지 않는다.
- 고정 도착률 모드는 예정 제출 시각, 실제 제출 시각, 완료 시각을 기록한다. 부하 생성기 자체의 밀림을 숨기거나 늦어진 요청을 조용히 버리지 않는다. 예정 시각 기준 지연과 실제 제출 기준 지연을 구분한다.
- 요청별 단조시계 지연을 기록하고 nearest-rank 방식으로 p50/p95/p99를 계산한다. 읽기·쓰기·부하 종류별로 나누며 오류/거절/timeout을 성공 지연에 섞어 성능이 좋아 보이게 하지 않는다.
- offered/completed/successful RPS, HTTP 상태·오류 코드별 수, timeout과 미완료 요청 수, generator lag를 함께 기록한다. timeout 표본은 정확한 완료시간을 모르는 관측으로 표시한다.
- 서버 지표는 측정 전후 차이를 쓴다. 준비·워밍업 요청이 측정 지표에 섞이지 않게 한다.
- 서버 RSS/가능하면 peak RSS와 시작→health ready 시간을 기록한다. 측정 수단·샘플 주기·추가 오버헤드를 명시한다.
- 동일 PC/컨테이너 자원 제한, CPU·메모리·저장 위치, OS/kernel, 컴파일러, 라이브러리, 이미지 식별자, 커밋·명령·seed를 저장한다. Windows bind mount와 컨테이너 내부 파일시스템을 혼용하지 않는다.
- 부하 생성기가 병목이면 client 수·프로세스 구성을 조정하고 다시 기록한다. 비교군의 실행 순서를 번갈아 배치하고 무관한 서버를 동시에 부하 실행하지 않는다.

## E. 실행 단계와 결과물

1. 작은 데이터·짧은 실행으로 fixture, 결과 정확성, 출력 형식, 정리 동작을 검증한다. 이 결과로 p99 성능 결론을 내리지 않는다.
2. pilot로 낮은 부하·포화 근처·과부하의 세 도착률을 정한다. 서로 다른 비교군에 같은 도착률을 적용한다.
3. 정식 실행은 각 조건에 워밍업 5초 이상, 측정 30초 이상, 독립 반복 3회로 시작한다. 전체 matrix의 예상 실행량을 runner가 먼저 출력한다. 표본이 적은 클래스의 p99는 결론을 유보하고 해당 측정을 연장한다.
4. 원시 요청 결과 JSONL, 환경·설정 JSON, 요약 CSV, 서버 로그와 지표 snapshot을 `docs/phase3-benchmarks/<run-id>/` 아래 보관한다. 보고서에는 결과 파일과 재현 명령을 연결한다. 대용량 원시 파일은 크기를 확인한 후 별도 보관 여부를 결정하고 조용히 커밋하지 않는다.
5. 비교 보고서에 처리량·읽기/쓰기 tail latency·오류율·대기 분류·메모리·한계를 적는다. 반복별 결과와 변동을 남기고 단일 최댓값만 선택하지 않는다.
6. 기존 sanitizer 실행 기록은 실제 검증 환경과 재현 제한을 명시하도록 보완한다. 지원 여부 확인 없이 이전 보고를 새 실행 결과로 인용하지 않는다.

## 완료 기준

- 지표 추가에 대한 테스트와 Release 회귀 테스트 통과.
- 다섯 부하와 worker 1·2·4·8의 실제 비교 결과 또는 실행하지 못한 조건과 사유가 식별됨. 필수 조건이 빠지면 전체 benchmark 완료로 표시하지 않음.
- 정상 결과의 정확성 검증, 오류/거절/미완료·generator 병목 기록이 있음.
- 동일 설정으로 재현할 명령·환경·원시 결과·요약 보고서가 있음.
- 4번 계획에 읽기 진행 여부, 읽기/쓰기 p95/p99, write/read gate 대기 근거를 전달함.
- '병렬 호출이 겹친다'와 '성능이 개선됐다'를 구별함. 확정된 사용자 SLO가 없으므로 임의의 지연 수치를 제품 요구사항으로 간주하지 않음.

## 제외 범위

성능 숫자를 맞추기 위한 C 엔진 변경, 인덱스 fanout 변경, 자동 인덱스 재구축, 공정성 정책 변경, 실행 중 SQL 취소, 전체 프로세스 메모리 상한 도입은 하지 않는다.

## 실행 기록 — 진행 중

- 다섯 잠금 범주의 count/total/max와 기존 합계 호환을 구현했다. 엔진 및 HTTP 테스트에서 정확한 횟수, 합계, max 관계를 확인했다.
- 같은 reader 수를 유지하는 별도 `minidb_server_serial` 타깃과 Python stdlib 부하 생성기를 추가했다. Release CTest 6개 suite 및 직렬 서버 API 검사 3개가 통과했다.
- 초기 단일 프로세스 pilot에서 client CPU 코어 하나가 포화되어 4개 프로세스/32개 연결로 변경했다. 컨테이너는 CPU 8개분, RAM 6GiB이며 DB는 Linux overlay의 `/tmp`에 생성한다.
- 원시 자료 저장의 중복 압축을 없앴고 gzip member 병합 후 모든 프로세스의 레코드 수와 식별자 유일성을 검증했다. 변경 전 중단 실행 `closed/`는 정식 집계에서 제외한다. 새 실행의 첫 비교 쌍도 종료 정리와 겹칠 가능성을 배제하기 위해 마지막에 다시 측정해 대체한다.
- 정식 비교는 `docs/phase3-benchmarks/20261116/closed-v2/`(168개), `open/`(18개), `fallback/`(12개)에 저장한다. 고정 도착률은 pilot에서 관찰한 1,000/20,000/50,000 RPS를 동일하게 적용한다. 이 값이 모든 구성의 정확한 포화점을 뜻하지는 않는다. (이 정식 비교는 중단됐고, 커밋하지 않은 `closed*`·`pilot*`·`smoke*` 결과는 2026-11-17에 삭제했다.)
- 스캔 부하는 표본 수가 작으므로 worker 4의 두 서버를 120초씩 3회 추가 측정한다. 그래도 적은 클래스의 p99는 확정적 결론을 유보하고 표본 수를 제시한다.
- TSan 런타임 실패 및 이전 sanitizer 기록과 현재 검증의 구분을 README와 구현 문서에 반영했다. 전체 측정과 공정성 평가는 아직 완료로 표시하지 않는다.
