# 9. 읽기·쓰기 큐 분리 — 문제 범위와 작업 계획

작성일: 2026-11-17  
기준 커밋: `82222b7`  
상태: 완료(2026-11-17). 구현 `5a4c2e7`, 쓰기 worker 기본값 2로 채택. 결과와 결정은 [11절](#11-14단계-결과-2026-11-17)에 있다.

## 1. 지금 구조

```text
HTTP I/O 스레드(--io-threads, 기본 2)
  요청 검사: JSON, UTF-8, SQL 바이트 상한
  → pool.try_submit: 큐 하나(FIFO), 용량 --queue-capacity 256개, --queue-bytes 16 MiB
SQL worker(--workers, 기본 4)
  → 큐 만료 검사: 큐에서 기다린 시간만 본다(--queue-timeout-ms 5000)
  → engine.execute(worker, sql)
      파싱(여기서 처음으로 INSERT인지 SELECT인지 안다)
      INSERT: 배타 gate → C 실행
      SELECT: 공유 gate → worker 자기 TableReader로 C 실행
```

| 사실 | 근거 |
|---|---|
| 요청 종류는 worker가 파싱한 뒤에야 안다. 큐는 종류를 모른다 | [main.cpp](../../../server/main.cpp) `/query` 핸들러, [engine.cpp](../../../server/engine.cpp) `run` |
| 큐는 하나이고 용량·바이트 상한과 만료를 모든 요청이 공유한다 | [thread_pool.hpp](../../../server/thread_pool.hpp) |
| gate는 쓰기 우선이다. 기다리는 writer가 하나라도 있으면 새 reader가 들어가지 못한다 | [writer_preferred_gate.hpp](../../../server/writer_preferred_gate.hpp) `can_read` |
| INSERT를 잡은 worker는 gate를 기다리는 동안에도 worker 하나를 차지한다 | `engine.cpp` `std::unique_lock<EngineGate> write_gate(gate)` |
| 큐 대기 지표는 전체 합계뿐이다. 종류별로 나뉘지 않는다 | `PoolStats.queue_wait_us` |

## 2. 문제 후보

큐 분리로 풀려는 문제를 메커니즘별로 나눈다. **아직 어느 것도 측정으로 확인하지 않았다.**

| 번호 | 문제 | 일어나는 방식 |
|---|---|---|
| P1 | INSERT 몰림이 worker를 붙잡음 | 큐 앞쪽에 INSERT가 worker 수 N개 이상 이어지면 N개 worker가 모두 INSERT를 꺼낸다. 하나만 실행되고 나머지 N−1개는 gate 앞에서 기다린다. 그 뒤의 SELECT는 큐에서 꺼내 줄 worker가 없다. |
| P2 | 기다리는 writer가 여러 개라 reader가 계속 밀림 | P1 상황에서는 기다리는 writer가 거의 항상 있다. 그래서 쓰기 우선 gate가 새 reader를 계속 막는다. B2에서 관찰한 읽기 지연의 원인이다. |
| P3 | INSERT 폭주가 SELECT를 거절시킴 | 큐 용량과 바이트 상한을 같이 쓰므로, INSERT가 큐를 채우면 SELECT도 `QUEUE_FULL`을 받는다. 1,000행 INSERT는 최대 64 KiB라 256개면 16 MiB 상한에 닿는다. |
| P4 | 반대 방향: 긴 스캔 뒤에 INSERT가 줄 섬 | 스캔이 worker를 모두 차지하면 INSERT는 이미 실행 중인 스캔뿐 아니라 큐에 먼저 들어온 스캔까지 기다린다. B1의 100만 행 스캔은 약 5초다. |

함께 알아둘 것:
- **만료 기준.** 지금 만료는 큐 대기만 본다. 쓰기 전용 worker가 생기면 INSERT는 큐에서 바로 꺼내진 뒤 gate 앞에서 기다린다. 이 대기는 만료에 걸리지 않는다. 5절 D5에서 다룬다.

## 3. 이미 있는 근거와 빈칸

| 측정 | 결과 | 큐 분리에 주는 의미 |
|---|---|---|
| B2 (쓰기 99%, worker 8, 연결 32, 고정 동시성) | 큐 평균 대기는 모든 요청에서 약 1.5ms. 읽기는 read gate에서 평균 24ms를 기다림. 원인은 큐가 아니라 쓰기 우선 gate로 판정 | 이 조건에서는 큐가 주원인이 아니었다. 다만 P2(기다리는 writer가 여러 개)는 gate 대기로 나타나므로, 큐 분리가 gate 대기를 줄일 가능성은 남아 있다 |
| B5 (깨우기 개선 후 같은 조건) | 읽기 p99 약 130 → 20ms, 처리량 약 2.5배 | 큐 분리 효과를 비교할 현재 기준값 |
| B3 (공정 gate 후보) | 읽기 p99 약 4.4ms. 처리량 −34%, 쓰기 p99 +30%. 채택하지 않음 | 큐 분리가 처리량을 잃지 않고 읽기 지연을 줄이면 공정 gate의 대안이 된다 |
| B1 (스캔 90%·쓰기 10%) | 스캔 잠금 제거 뒤 스캔 중 INSERT p99가 1.8 → 0.4초 | P4가 아직 0.4초 남아 있다. 이 중 얼마가 큐 대기인지는 측정하지 않았다 |

빈칸:
1. **종류별 큐 대기가 없다.** SELECT가 큐에서 얼마나 기다렸는지 따로 알 수 없다.
2. **큐가 길어지는 조건을 재지 않았다.** 지금까지는 연결 32개·worker 8개의 고정 동시성이라 큐에 최대 24개만 쌓였다. 도착률이 처리 능력을 넘는 고정 도착률 부하(P1, P3 조건)는 재지 않았다.
3. **다중 행 INSERT를 섞은 서버 측정이 없다.**
4. **종류별 `QUEUE_FULL` 수가 없다.**

따라서 이 계획은 **0단계에서 문제를 먼저 확인**하고, 확인된 문제에 맞춰 범위를 줄이거나 중단할 수 있게 짠다.

## 4. 범위

포함:
- 요청 수락부터 엔진 실행까지의 **스케줄링**: 요청 종류 분류, 읽기·쓰기 큐 분리, 큐별 용량, 쓰기 worker 수, 쓰기 쪽 만료 기준.
- 큐별 지표와 종류별 큐 대기 지표.
- 종료 시 두 큐 모두 비우기(drain)를 지금과 같은 계약으로 유지.

제외:
- **gate 정책 변경.** 04의 쓰기 우선 유지 결정을 바꾸지 않는다. 큐 분리 때문에 gate 대기 양상이 달라지면 그 결과를 기록만 한다.
- 실행 중 SQL 취소, 클라이언트별 제한, 요청 간 묶음 쓰기, `fsync`.
- 큐 분리를 넘어선 우선순위 정책(가중치, 나이 기반 승격 등).
- C 엔진 변경. 예외로, 분류용 함수 하나(D1 a안)만 추가할 수 있다.

유지할 계약:
- HTTP 요청·응답 형식, `write_outcome` 의미, 결과 제한, 종료 drain 계약.
- `/metrics`의 기존 `pool` 필드. 이름과 의미를 유지하고 새 필드만 추가한다.
- 기존 테스트 중 공유 큐 하나를 전제한 테스트는 6절 3단계에서 기대값을 바꾸며, 무엇을 왜 바꿨는지 기록한다.

## 5. 설계에서 정할 것

| 번호 | 정할 것 | 선택지 | 권장 |
|---|---|---|---|
| D1 | 분류 위치 | (a) C 파서의 lexer로 첫 키워드만 읽는 함수를 추가하고 I/O 스레드에서 호출<br>(b) I/O 스레드에서 전체 파싱 후 `Statement`를 큐로 넘김<br>(c) worker가 파싱한 뒤 다른 큐로 다시 넣음 | **(a).** 첫 토큰만 읽어 비용이 작고, 주석·대소문자 규칙이 실제 파서와 같다. 엔진은 지금처럼 다시 전체 파싱하므로, 잘못 분류돼도 성능만 영향받고 결과는 맞다. (b)는 64 KiB 파싱을 I/O 스레드에서 하게 되고 엔진 API도 바꿔야 한다. (c)는 큐를 두 번 거친다 |
| D2 | 쓰기 worker 수 | 1개 / 2개 / 옵션 | **기본 1개, `--write-workers` 옵션.** INSERT는 어차피 gate에서 하나씩만 실행되므로 1개로 실행 병렬성을 잃지 않는다. 다만 지금은 여러 worker가 파싱을 겹쳐 하는데, 1개면 파싱도 직렬이 된다. 4단계에서 1개와 2개를 비교한다 |
| D3 | worker 번호와 reader 핸들 | 쓰기 worker에도 reader 핸들을 줌 / 주지 않음 | **줌.** 엔진의 reader 수를 읽기 worker 수 + 쓰기 worker 수로 둔다. 잘못 분류된 SELECT가 쓰기 쪽에 와도 실행된다. 인덱스는 공유하므로 reader 하나의 비용은 FILE 핸들 하나다 |
| D4 | 큐별 용량 | 기존 옵션을 큐마다 적용 / 기존 옵션은 읽기 큐, 쓰기 큐에 새 옵션 / 전체를 나눠 가짐 | **기존 옵션을 큐마다 적용.** 옵션 의미가 단순하다. 대신 최대 대기 메모리가 2배(32 MiB)가 된다. 문서에 적는다 |
| D5 | 쓰기 쪽 만료 | (a) 지금처럼 큐에서 꺼낼 때만 검사<br>(b) gate를 잡은 뒤 한 번 더 검사하고, 지났으면 쓰지 않고 `QUEUE_TIMEOUT`·`not_started` | **(b).** 쓰기 worker 1개 구조에서는 대기가 큐가 아니라 gate 앞으로 옮겨 가므로, (a)로는 만료가 사실상 사라진다. 옵션 설명이 이미 "SQL 실행 전 만료"라서 (b)가 설명과 맞다. gate에 시간 제한 대기를 넣는 것은 하지 않는다(04의 제외 범위). 엔진 `execute`에 마감 시각 인자를 추가해야 한다 |
| D6 | 지표 | 기존 `pool`을 합계로 유지하고 `pools.read`·`pools.write` 추가 | **권장대로.** 종류별 큐 대기(합계·최대)와 종류별 `QUEUE_FULL`도 추가한다 |
| D7 | 풀 구현 | `ThreadPool` 두 개 / 큐 두 개짜리 새 풀 | **`ThreadPool` 두 개.** 클래스와 기존 풀 테스트를 그대로 쓴다. 종료 시 둘 다 `shutdown`하고, 쓰기 쪽 worker 번호는 읽기 worker 수만큼 밀어 준다 |

D2·D5의 부수 효과: 쓰기 worker가 1개면 gate 앞에서 기다리는 writer도 최대 1개다. writer가 gate를 놓은 순간 다음 INSERT를 꺼내 다시 기다리기 전까지 reader가 들어갈 틈이 생긴다. gate 정책은 그대로인데 reader 대기 양상이 달라질 수 있다. 이것은 gate 정책 변경이 아니라 스케줄링의 결과로 기록한다.

## 6. 작업 단계

### 0단계: 문제 확인 (구현 여부를 정하는 관문)

1. **종류별 큐 대기 지표 추가.** worker 람다에서 작업 시작 시각과 `queued_at`의 차이를 결과 종류(INSERT / SELECT / 파싱 실패)별로 합계·최대로 센다. `/metrics`에 필드만 추가한다. 큐 분리 뒤에도 그대로 쓴다. 이 변경은 따로 커밋한다.
2. **현재 HEAD를 측정한다.** 조건마다 워밍업 5초, 측정 30초, 3회 반복. worker 8이다.

| 조건 | 부하 | 확인할 문제 |
|---|---|---|
| S1 | `write99` 고정 동시성(B5와 같은 조건) | P2. 기준값 재확인 |
| S2 | `write90` 고정 도착률. 1회 짧은 예비 측정으로 처리 능력을 잰 뒤, 그 1.5배 도착률 | P1, P3. 큐가 실제로 길어지는 조건 |
| S3 | `scan_write` 고정 동시성(B1과 같은 조건) | P4 |

3. **판정 규칙.** 임의의 ms 기준은 두지 않는다.
   - **P1/P2 확인:** S1이나 S2에서 SELECT의 큐 대기가 SELECT 전체 지연에서 큰 비중을 차지한다. 또는 INSERT만 완료되고 SELECT가 진행하지 못하는 구간이 3회 모두 관찰된다.
   - **P3 확인:** S2에서 SELECT가 `QUEUE_FULL`을 받는다.
   - **P4 확인:** S3에서 INSERT의 큐 대기가 INSERT 전체 지연에서 큰 비중을 차지한다.
   - **하나도 확인되지 않으면** "현재 부하 범위에서 문제 미확인"으로 기록하고 구현하지 않는다.
   - **일부만 확인되면** 범위를 줄인다. 예를 들어 P3만 확인되면 용량 분리만 한다.

### 1단계: 설계 확정
0단계 결과로 D1~D7을 정하고 이 문서를 갱신한다. 사용자 확인을 받는다.

### 2단계: 구현
- C: `parser_peek_kind`(가칭)와 단위 테스트. 공백·주석·대소문자, 빈 입력, 잘못된 첫 토큰은 읽기 쪽으로 보낸다.
- 서버:
  - `ThreadPool` 두 개와 분류 후 제출.
  - 엔진 reader 수와 worker 번호 배치(D3).
  - 쓰기 쪽 만료 재검사(D5)와 `execute`의 마감 시각 인자.
  - 옵션 `--write-workers`, 지표(D6), 도움말.
- 비교용 타깃 `minidb_server_serial`, `minidb_server_fair`도 같은 `main.cpp`를 쓰므로 함께 빌드되는지 확인한다.

### 3단계: 테스트

| 테스트 | 확인할 것 |
|---|---|
| 분류 단위 테스트 | 주석·공백 뒤 키워드, 대소문자, 잘못된 입력 |
| 용량 분리 (API) | 쓰기 큐 용량을 작게 두고 쓰기 쪽을 막아 둔 상태에서 INSERT를 채운다. 그래도 SELECT는 `QUEUE_FULL` 없이 처리된다 |
| 스캔 뒤 INSERT (제어 API) | 읽기 worker 1개가 스캔에 붙잡혀 있고 읽기 큐에 스캔이 더 쌓여 있다. INSERT는 진행 중인 스캔만 기다리고, 쌓인 스캔보다 먼저 끝난다 |
| 쓰기 만료 (제어 API) | 기존 `test_queue_expiry_while_worker_is_held`를 고친다. INSERT가 큐 대신 gate 앞에서 기다려도 `QUEUE_TIMEOUT`·`not_started`이고 기록되지 않는다 |
| 종료 drain (제어 API) | 기존 `test_sigterm_drains_a_confirmed_pending_queue`를 고친다. 대기 위치가 `pools.write`로 바뀐다. 수락한 INSERT가 모두 저장되는 계약은 같다 |
| 기존 회귀 | `make test`, 서버 Release `ctest` 6개, TSan(엔진·풀·gate 테스트) |

기존 테스트 두 개는 **공유 큐에서 INSERT가 스캔 뒤에 기다린다**는 지금 구조를 전제로 한다. 계약(만료되면 기록 안 함, 수락한 INSERT는 종료 전에 저장)은 유지하고, 관찰 위치(`pool.queued`)만 바꾼다.

### 4단계: 측정
0단계와 같은 S1~S3을 변경 전후로 번갈아 3회씩 잰다. S1·S2는 쓰기 worker 1개와 2개를 함께 잰다.

판단 기준(04 D절과 같은 원칙):
- 확인된 문제의 지표(SELECT 진행, SELECT p99, 종류별 `QUEUE_FULL`, INSERT 지연)가 반복 변동을 넘어 개선된다.
- 처리량과 쓰기 지연이 반복 변동을 넘어 나빠지지 않는다.
- 개선과 악화가 함께 나오면 자동으로 채택하지 않는다. 결과와 선택지를 기록하고 사용자와 정한다.

### 판정

| 문제 | 판정 | 근거 |
|---|---|---|
| P1. SELECT가 INSERT 뒤에서 큐 대기 | **확인 (S2)** | SELECT 서버 시간의 72–75%가 큐 대기다. FIFO라 SELECT 큐 대기는 INSERT 큐 대기와 같다. 다만 write gate 대기는 0.16ms로 작아서, 대기의 원인은 "worker가 gate 앞에 붙잡힘"보다 "쓰기 과부하로 쌓인 큐 뒤에 줄 섬"이다. 큐를 나누면 어느 쪽이든 SELECT는 INSERT 줄을 건너뛴다 |
| P2. 기다리는 writer 여러 개 때문에 reader가 밀림 | **따로 구분하지 못함** | S1에서 SELECT 서버 시간의 대부분(약 93%)이 read gate 대기다. 이것이 기다리는 writer 수 때문인지는 쓰기 worker를 1개로 줄여 봐야 안다. 4단계에서 S1의 read gate 대기로 확인한다 |
| P3. INSERT 폭주가 SELECT를 거절시킴 | **확인 (S2)** | 3회 모두 SELECT가 `QUEUE_FULL`을 받았다(129–232건) |
| P4. 긴 스캔 뒤에 INSERT가 줄 섬 | **확인 (S3)** | INSERT 서버 시간의 85%(약 243ms)가 큐 대기다. 실행 중 스캔 때문인 write gate 대기는 약 43ms다 |

결론: 판정 규칙상 **범위를 줄일 근거가 없다.** P1·P3·P4가 확인됐으므로 6절의 전체 범위(분류, 큐 두 개, 큐별 용량, 쓰기 worker, 쓰기 쪽 만료, 지표)를 1단계 설계 대상으로 둔다.

기대 효과와 한계(4단계에서 확인할 것):
- S2: SELECT 큐 대기(약 5ms)가 거의 사라지고, SELECT `QUEUE_FULL`이 0건이 되어야 한다. 쓰기 쪽은 여전히 과부하라 INSERT의 `QUEUE_FULL`은 남는다.
- S3: INSERT 지연이 큐 대기(약 243ms)만큼 줄어 write gate 대기 수준(약 43ms + 실행)에 가까워져야 한다. 스캔끼리의 큐 대기(74%)는 큐 분리로 줄지 않는다.
- S1: 큐 대기 비중이 4%라 큐 자체로 얻을 것은 거의 없다. 쓰기 worker 1개가 read gate 대기를 바꾸는지가 관전 포인트이고, 쓰기 처리량이 떨어지지 않는지 함께 본다.

### 해석

- **읽기 쪽은 목표대로 개선됐다.** 쓰기 과부하(S2)에서 SELECT는 더 이상 INSERT 뒤에 줄 서지 않는다(읽기 p99 약 25 → 1–2ms, SELECT `QUEUE_FULL` 0건). 쓰기 99%(S1)에서도 읽기 p99가 약 18 → 1.4ms다.
- **S1의 읽기 개선은 gate 대기 감소에서 왔다.** read gate 평균 대기가 약 1.6ms에서 0.01–0.04ms가 됐다. gate 앞에서 기다리는 writer가 최대 8개에서 1~2개로 줄어 reader가 들어갈 틈이 생겼다(5절 D2의 부수 효과). 0단계에서 따로 구분하지 못한 P2가 실제로 있었다는 뜻이다. gate 정책은 바꾸지 않았다.
- **ww1은 쓰기에서 퇴행한다.** 
  - S2: 100행 INSERT의 파싱이 worker 하나에서 직렬로 일어나 쓰기 처리량이 19% 줄었다.
  - S3: INSERT마다 실행 중 스캔이 빠질 때까지(평균 약 85ms) gate 앞에서 기다린다. 그동안 쓰기 worker가 하나뿐이라 다음 INSERT가 쓰기 큐에서 기다린다. 도착(초당 약 10건)이 처리 능력(초당 약 12건)에 가까워 큐가 길어졌다. 변경 전에는 worker 8개가 함께 gate 앞에서 기다리다 한 번의 쓰기 구간에 연달아 처리됐다.
- **ww2는 세 조건 모두에서 변경 전보다 같거나 낫다. 예외는 S3 스캔 지연 약 5% 증가다.** INSERT가 큐 대신 gate 앞에서만 기다리므로 쓰기 구간이 더 자주 생기고, 그만큼 스캔이 조금 더 밀린다. 처리량은 같다.
- ww4는 ww2와 반복 변동 안에서 같다. 2개를 넘겨 얻는 것은 없었다.
- 처리량 참고: B5에서 "부하 생성기 상한"으로 본 약 3.3만 RPS를 ww2가 넘었다(약 3.9만). 그때의 상한 판단은 생성기가 아니라 서버 쪽 대기였을 수 있다.

### 판정

계획의 규칙("개선과 악화가 함께 나오면 자동으로 채택하지 않는다")에 따라 사용자에게 결정을 요청한다.
- 기본값 ww1(1단계 결정): S2 쓰기 처리량 −19%, S3 INSERT p99 2–4배 악화. **채택 기준 미충족.**
- 기본값 ww2: 확인된 문제(P1·P2·P3·P4) 지표가 모두 반복 변동을 넘어 개선. 처리량과 쓰기 지연은 나빠지지 않음. 악화는 S3 스캔 p50·p99 약 5% 하나.

**결정 (2026-11-18, 사용자):** 쓰기 worker 기본값을 **2**로 채택한다. 1단계 D2의 "기본 1개"를 이 측정 결과로 바꾼다. 스캔 지연 약 5% 증가는 알려진 비용으로 기록한다. ww2는 세 조건을 모두 이미 측정했으므로 추가 측정은 하지 않았다. 기본값 변경 뒤 Release `ctest`를 다시 실행했다(아래 5단계).

### 5단계: 문서
- [`server/README.md`](../../../server/README.md): `--write-workers`(기본 2), 큐별 상한과 대기 메모리 2배, 분류 규칙, `QUEUE_TIMEOUT`의 두 검사 시점, `pool`·`pools.*` 지표.
- [`docs/implementation-phase3.md`](../../implementation-phase3.md): 요청 흐름 그림, 5절 큐·만료·종료, 7절 계측 표, 쓰기 worker 기본값 2의 근거.
- [`server/benchmarks/README.md`](../../../server/benchmarks/README.md): `--variant`, `bulk90`, `digest.py`.
- 루트 [`README.md`](../../../README.md): Phase 3 측정 요약과 알려진 한계.

남은 한계:
- 쓰기 우선 gate 정책은 그대로다. 실행 중인 스캔이 끝날 때까지 INSERT가 기다리는 것(S3 write gate 평균 약 57ms)은 남아 있다.
- 읽기 큐 안에서 스캔끼리의 대기(S3 스캔 서버 시간의 약 70%)는 큐 분리 대상이 아니다.
- 쓰기 과부하 시 INSERT는 여전히 `QUEUE_FULL`을 받는다. 쓰기 큐가 따로 있어 SELECT에 번지지 않을 뿐이다.
- 측정은 worker 8 하나만 했다. worker 1·2·4에서의 효과는 재지 않았다.

## 완료 기준

- 0단계에서 끝나는 경우: 측정 결과와 "문제 미확인" 또는 "범위 축소" 판단이 이 문서에 기록되어 있다.
- 구현하는 경우: 3단계 테스트가 통과하고, 4단계 비교 결과와 채택 여부 판단, 바뀐 계약(만료 의미, 지표, 옵션)이 문서에 반영되어 있다.
- 실행 기록에 수정 파일, 실제 명령, PASS/FAIL/미실행, 남은 한계를 남긴다.
