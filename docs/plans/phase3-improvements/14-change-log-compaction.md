# 14. 변경 기록과 나중 정리 — 한 행 변경을 행 수와 무관하게

작성일: 2026-11-18  
기준 커밋: `f89f37c` (브랜치 `feat/phase3-cpp`)  
상태: **조건부 계획, 보류(2026-11-18).** 16번 뒤 100만 행 한 행 변경이 컨테이너 85 ms로 2절 조건(100 ms 초과)에 해당하지 않는다. [11번](11-modify-cost.md) 측정과 [12번](12-two-phase-rewrite.md) 결과로도 부족할 때만 진행한다. 진행 전에 사용자 확인을 받는다.

## 1. 문제

UPDATE·DELETE는 한 행만 바꿔도 파일 전체를 읽고 다시 쓴다. 비용은 O(전체 행 수)다.

- 12번은 이 시간 동안 SELECT가 멈추지 않게 할 뿐이다. 비용 자체는 그대로다.
- 쓰기 처리량은 12번 뒤에도 "UPDATE 한 번 = 파일 한 번 재작성"에 묶인다.

## 2. 진행 조건

다음 중 하나가 측정으로 확인될 때만 진행한다.

- 12번 적용 뒤에도 100만 행 UPDATE의 확정 단계(배타 gate 보유)가 100 ms를 넘는다.
- 사용 패턴상 UPDATE·DELETE가 초당 여러 번 필요하다(사용자 요구로 확인). 그런데 11번 측정상 한 번에 수백 ms 이상 걸린다.

둘 다 아니면 이 계획은 보류로 둔다. 파일 형식이 바뀌는 큰 변경이라 필요가 확인되기 전에는 하지 않는다.

## 3. 범위

포함:

- 변경 기록 파일 `users.log`를 추가한다. 구조:
  - `U\t<id>\t<name>\t<age>\n`: 행 교체.
  - `D\t<id>\n`: 행 삭제.
  - 파일 끝에 추가만 한다.
- 시작할 때 `users.tsv`를 읽은 뒤 `users.log`를 재생해 인덱스를 만든다.
- 인덱스 값의 의미를 바꾼다.
  - 지금은 "`users.tsv` 안의 위치"다.
  - 바꾼 뒤에는 "어느 파일(`users.tsv`·`users.log`)의 어느 위치"가 된다. 삭제된 ID는 인덱스에서 뺀다.
- SELECT 스캔은 `users.tsv`를 저장 순서대로 읽는다.
  - 각 행에 대해 인덱스가 같은 위치를 가리키는지 확인한다.
  - 같으면 그 행을 출력한다.
  - 다르면 그 행이 교체 또는 삭제된 것이다. 교체된 행이면 `users.log`의 최신 행을 출력하고, 삭제된 행이면 건너뛴다.
  - 결과 순서는 지금과 같다.
- 정리(compaction): `users.log`가 `users.tsv` 크기의 일정 비율을 넘으면 다음 쓰기 때 실행한다. 비율 후보는 25%다.
  - 지금의 `table_rewrite`로 기록을 반영한 새 `users.tsv`를 만든다.
  - 그 뒤 `users.log`를 비운다.
  - 순서와 `fsync`는 10번 후속과 같은 방식을 쓴다.
- UPDATE·DELETE의 `WHERE id = N`은 정리가 필요 없으면 기록 한 줄만 추가한다. 비용은 O(log n)과 fsync 정책에 따른 비용이다.
- `WHERE age = N` 또는 조건 없는 문장은 스캔이 필요하다. 이 경우는 지금처럼 전체를 다시 쓰거나 기록 여러 줄을 추가한다. 둘 중 무엇으로 할지는 설계 단계(5절 1단계)에서 정한다.

제외:

- 트랜잭션, MVCC, 여러 문장의 원자성.
- `users.tsv` 형식 자체의 변경. 기존 파일은 그대로 읽힌다.
- 다른 프로세스와의 동시 접근.

## 4. 영향과 위험

| 항목 | 영향 |
|---|---|
| 파일 형식 | `users.log`가 생긴다. 이 파일이 있는 데이터 폴더는 구버전이 잘못 읽는다. 구버전은 기록을 무시하므로 지운 행이 되살아난다. 버전 표시와 구버전 거부 방법이 필요하다. |
| CLI 호환 | `users.tsv`만 보는 외부 도구나 테스트(`cli_test.py`의 `env.data()`)의 기대가 바뀐다. 정리 전에는 파일 내용이 SELECT 결과와 다르다. |
| 스캔 비용 | 행마다 인덱스를 확인하는 비용이 더해진다. O(n log n)이다. 기록이 쌓이면 `users.log`를 무작위로 읽는 비용도 생긴다. 정리 비율로 상한을 둔다. |
| 내구성 | 기록 한 줄을 추가할 때 `fsync` 정책을 INSERT(fflush만)와 맞출지 정해야 한다. 맞추면 정전 시 마지막 변경을 잃을 수 있다. 10번 후속처럼 "전체 손실"은 생기지 않는다. |
| 12번과의 관계 | 정리 단계는 12번의 두 단계 방식을 그대로 쓴다. 12번이 먼저 끝나 있어야 한다. |
